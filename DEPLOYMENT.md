# Free-tier launch: Render + Neon

The repository includes a Dockerfile and `render.yaml` for a single Render web service. Rust serves both `/api` and the built React app. Neon provides persistent PostgreSQL storage over TLS.

## 1. Prepare accounts and source

Create your own accounts at https://dashboard.render.com/register and https://console.neon.tech/signup. Select the free plans. Push the `codex/public-release` branch to your GitHub repository. Run the Release checks workflow before inviting users.

## 2. Create the database

In Neon, create a project on the Free plan and select a region close to your Render service. Copy the PostgreSQL connection string from the Connect panel. Retain `sslmode=require` (or the TLS options supplied by Neon). Use the project owner connection initially so the app can run its schema migrations.

Do not paste this connection string into chat, commit it, or put it in a frontend `VITE_` variable. It belongs only in the backend service's `DATABASE_URL` secret.

## 3. Deploy the application

In Render, choose New → Blueprint and connect this GitHub repository. Select the release branch, or merge it into main after review. Render reads `render.yaml`.

- Confirm the web service uses the Free instance.
- Enter the Neon connection string for `DATABASE_URL` when prompted.
- `JWT_SECRET` and `ROCKET_SECRET_KEY` are generated by Render.
- No frontend API URL is needed: frontend requests use `/api` on the same host.
- Do not set `ALLOWED_ORIGINS` for this same-origin deployment.

Deploy and wait for `/api/health` to return `ok`. The build compiles React and Rust; the app runs migrations before accepting traffic. Open the returned HTTPS `onrender.com` URL.

If using a manually created Render Web Service instead, choose Docker with the repository root as context, Dockerfile `./Dockerfile`, Free plan, health check `/api/health`, and the same environment variables. `PORT` is supplied by Render and read by the app.

## 4. Verify the actual public release

Use two test accounts and disposable content:

1. Register, sign out, and sign back in.
2. Create a private deck with two cards. Reload its direct URL.
3. Edit a card, rename the deck, and study it. Reload: the saved due count must change.
4. Confirm a second user cannot open or edit the private deck.
5. Share the deck. The second user can study it but cannot edit it; their progress must be independent.
6. Unshare it and confirm the second user's access ends.
7. Confirm `/api/rows` is 404 and `/api/deck` without a token is 401.
8. Check the app on a phone, and only delete the disposable test data.

## Free-tier tradeoffs

Render's free web service sleeps after inactivity, so the first request can take time to wake up. Free compute and Neon storage/compute have quotas. Check the current limits before sharing widely. Use Neon rather than Render's expiring free PostgreSQL offering for this launch.

- Render free services: https://render.com/docs/free
- Render Blueprint reference: https://render.com/docs/blueprint-spec
- Neon plans: https://neon.com/docs/introduction/plans

## Data and launch limits

Keep a database export before migrations or destructive maintenance. The app does not provide automated off-platform backups, password recovery, email verification, account deletion, file uploads, or Anki synchronization. A forgotten password requires administrator assistance; do not promise self-service recovery. Review scheduling is intentionally simple and described in README.md.

JWT sessions expire after 24 hours. Sign out clears the browser token. Changing the JWT secret invalidates all sessions. Authentication requests have in-memory global and per-username limits to bound password-hashing load; limits reset on restart and do not replace host-level abuse controls.

## Rollback

Render can redeploy a previous build, but application rollback does not undo migrations or restore deleted cards. Restore data only from a verified database backup when necessary. Do not delete the Neon project when replacing an application deployment.
